## 审查 .gitignore 的 database/ 忽略规则（结论：忽略是对的，但有两处漏洞）

逐列核对 `server/db/schema.js` 后确认：库里没有任何「文件里找不到来源」的数据。

- category/tag（含 cover、position←数组下标）← `data/meta.json`
- article（title/summary/category_id/status/reads/created_at/updated_at）← `data/articles/<id>.json`
- article_tag ← 文章的 `tagIds`
- app_meta 只有 `schema_version` 一个 key，无业务数据
- 文章 id 是 `crypto.randomUUID()`，不依赖数据库自增 → 不会 id 错配
- 没有任何 `UPDATE article SET reads` 路径（reads 只在 create/update 时随 JSON 落盘）→ 阅读量也不会丢
- `server/index.js:24` 每次启动都 `rebuildIndex()`；`db/index.js` 在 schema_version 不一致时整库 DROP 重建

**发现并修掉的问题（已改 .gitignore）：**

1. `data/index.db` 早期遗留的旧库（45KB，代码里零引用），**历史上被 git 跟踪了** —— 与「库不进仓库」的规则矛盾。
   已在 .gitignore 加 `data/index.db`，还需用户自己跑 `git rm --cached data/index.db`（不代提交）。
2. `data/articles/*.tmp`（原子写残留，当前有一个 `c3ca8c85-....json.tmp`）会被当成未跟踪文件 —— 已加 `data/articles/*.tmp`。

## 索引库的运行时行为（用户追问，已澄清）

- **启动**：`server/index.js:24` **无条件**全量 rebuildIndex()（不是「版本不一致才建」），先 DELETE 四张表再重灌。11 篇毫秒级。
- **作用**：只做查询加速层 —— 列表筛选（category+tag+q 叠加）、`countByCategory/Tag`、`titleExists` 标题查重走 SQL。
  ⚠️ 正文**不进库**：详情现读文件 `readArticleFile()`；全文搜索 `searchArticles()` 扫文件（注释明写「索引库 LIKE 只覆盖标题摘要，正文必须走文件层」）。
- **运行时增量更新**：每条写路径都是「先写文件 → 再改库」双写 ——
  新建 `writeArticleFile`+`insertArticle` / 保存 `writeArticleFile`+`updateArticleIndex` /
  自动保存 `writeArticleFile`+`touchArticle`（只更 updatedAt）/ 删除 `trashArticleFile`+`deleteArticle` /
  分类标签改动→`taxonomy.repo` 全量替换 + 写 meta.json。
- **方向严格单向 JSON → 库**：repo 层没有任何 `fs.writeFileSync`，库里 article 只有一个 `rel_path` 指针。库**从不**生成/改写 JSON。
- ⚠️ 唯一副作用：**绕过 API 直接改 JSON**（脚本/编辑器手改）库不会感知，列表页仍是旧数据，需重启后端才同步。
