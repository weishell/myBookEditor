## Shift+Enter 软换行（块内 `\n`）— 新增

用户需求：「Shift+Enter 相当于 `\n`，而不是一个新的插件（新块）」。

**根因（读 slate 源码确证）**：浏览器对 Shift+Enter 触发 `beforeinput(insertLineBreak)`，
slate-react 转成 `Editor.insertSoftBreak`；而本项目 slate 0.126.2 里它的实现是
**`Transforms.splitNodes(editor, { always: true })`** —— 直接拆块，根本不写 `\n`。
所以「Shift+Enter = 回车」这个假象，就是它就是拆块导致的。

**实现**：

- `src/events/keyboard/handleKeyDown.ts`：Enter 分支里 `e.shiftKey` 时改为
  `Transforms.insertText(editor, '\n')`（与代码块 `handleEnter` 里现成写法一致）；
  `isKeyConsumed` 里 Enter 一律返回 `true`；`Element` 从 slate 导入时起别名 `SlateElement`。
  稳健性：命中 void 块时返回 false 不写（void 子文本不参与渲染）。
- `src/index.css`：新增 `[data-slate-editor] [data-slate-string] { white-space: pre-wrap; }`。
  slate-react 把文本渲染进 `<span data-slate-string>`，默认 `white-space: normal`
  会把 `\n` 折叠成空格 → 看起来「没反应」。pre-wrap 后才真正折行。

**验证（真实 slate 探针）**：旧路径 `Editor.insertSoftBreak` → **2 个块**（bug 复现）；
新路径 `insertText('\n')` → **1 个块**，文本 `"hello\n world"`。`tsc -b` 0 报错。

## 已有约定（本轮查证，供复用）

- 代码块靠 `Transforms.insertText(editor, '\n')` + `CodeLine.module.less` 的 `pre-wrap` 实现换行——
  段落软换行就是把这套推广到所有块。
- 键盘事件唯一入口 `src/events/keyboard/handleKeyDown.ts`（core/index.tsx 的 `onKeyDown`），
  各键 handler 在 `src/events/keyboard/` 下。

## 列表项悬挂缩进（换行文字不再压到序号下面）

用户需求：有序列表换行后，文字不应跑到序号（`2.`）下面，应左对齐首行文字。

**现状成因**：`LilistPrefix` 渲染成一个 `inline-block` 的序号 span（`text-align:right` + 槽位宽度），
它是 `<p>`/`<h*>` 里的**行内首元素**；文字换行后回到块的**内容盒左缘**，于是压在序号下面。

**实现（悬挂缩进）**：给块加 `padding-left: <槽位>` + `text-indent: -<槽位>`，
首行被负缩进拉回左边（放序号），后续行停在 padding 处（与首行文字左对齐）。
槽位宽度 = 序号占位宽(`getLilistPrefixWidth`) + `6px`(前缀 margin-right)，**两处必须同源**，
否则对不齐。序号本身仍用 `min-width`（不是 width）：位数超出时方框变宽，
宁可首行文字右移几像素，也不让编号溢出压到正文。

- `lilist-model.ts`：新增 `getLilistPrefixWidth(element)` → UL `1.2em` / OL `1.6em` / 标题有序 `2.6em`（层级路径更长）。
- `LilistPrefix.tsx`：前缀内联 `minWidth = getLilistPrefixWidth(element)`。
- `Paragraph.tsx` / `Heading.tsx`：有 lilist 时给 `<p>`/`<h1>` 内联
  `paddingLeft: calc(W + 6px)`、`textIndent: calc(-1 * (W + 6px))`。

**验证**：用本机真实 Chrome 无头渲染了 5 组对比（现象复现 + 单/双位数 + 无序 + 标题），
对比图存 `.workbuddy/artifacts/lilist-hang-compare.png`。`tsc -b` 0 报错。

**已知边界**：块设为「居中对齐」的列表项，首行会被 `text-indent` 额外左移（列表极少居中，未处理）。

## 有序列表「修改编号值」加重复保护（默认不产生重复编号）

用户需求：列表 1,2,3,4,5 里把某项设成一个**已被占用**的编号时，默认不能出现重复号
（现状会得到 1,2,2,3,4）；应「顺延」——本项取「同组同层前一项 + 1」，其后各项整体顺延，
列表保持连续完整（1,2,3,4,5）。想故意重复（拆成 1,2 ｜ 2,3,4 两个列表）走**「开始新列表」**
再改值——那时本项是新组首项、前面没有同组同层项，自然不受约束（无需新增 UI）。

- `lilist-model.ts`：新增 `getPrevSameLevelListNumber(editor, path)`。
  口径完全对齐 `sortLilist`：段落按 `attrs.indent`、标题按 `attrs.level` 分层；
  同组 = 同 `list_id` + 同 `list_type`，且**同组可不连续**（「继续之前的编号」并入后相隔），
  所以向前扫描遇到非本组块要 **continue 而不是 break**；
  途中遇更浅层级 → 本层计数器已清空 → 返回 null（= 本层无前项，编号可自由设）。
- `lilist-commands.ts`：新增 `resolveLilistNumber(editor, path, value)`（= max(输入值, 前项+1)），
  `changeLilistNumber` 改走它。
- `LilistSettingPopover.tsx`：确认时用 **`resolveLilistNumber(...) !== currentNumber`** 代替原来的
  `v !== currentNumber` —— 否则「当前就是 2、再输 2」会被提前判成没改动而根本不执行，顺延也就没机会发生；
  同时保留「真没改动就不写」，避免点一下确定就把自动编号固化成锚点。

**探针实测（真实源码）**：① `1,2,[2],3,4` 再输 2 → `[1,2,3,4,5]`（用户用例 ✅）；
② 设不冲突的 5 → `[1,2,5,6,7]`；③ 组首项设 2 → `[2,3,4,5,6]`；④ 新组首项设 2 → `[1,2,2,3]`（拆列表路径仍可用）；
⑤ 缩进子项同层无前项 → `[1,1]`。`tsc -b` 0 报错。

## lilist 编号语义（备忘）

- `attrs.lilist = { list_type, list_id, list_number, list_custom, list_path? }`。
- `list_custom` = 用户指定的「锚点」：**以自身值为起点，只影响其后**的编号；非锚点项按层计数器顺延。
- 三个命令：`continueLilist`（并入前方组）/ `restartLilist`（本项+后方同组剥离成新组，首项锚点为 1）/ `changeLilistNumber`（设锚点值）。
- 任何结构变更后都要调 `sortLilist(editor, [listId], fromIndex)` 回写编号（增量：只从变更点起算）。

## ⚠️ 修正上面那版规则（用户明确否定「拒绝」）

上一条把规则做成了「**拒绝**用户输入」（把 2 夹成 3 且不改别的），用户很生气：
原话「你禁止你妈呢，还是重复，**我需要重新排序**，除非不是一个列表啊」。

正确语义 = **重排**，不是拒绝：

- **同一列表内编号永远严格递增、不重复**：锚点只允许「往后跳号」（设 5 → 5,6,7 可以）；
  锚点值 ≤ 本层计数器 → 视为**无效**，按顺序顺延，并**清掉 `list_custom`**
  （不清的话会把顺延值固化成新锚点，之后删掉前项会留空号）。
- **不同列表各自独立计数**，因此 `1,2 ｜ 2,3,4` 这种可见重复是合法的 —— 用户说「除非不是一个列表」。
- 手动要重复：`开始新列表`（拆组）→ 再 `修改编号值` → 得到 `1,2 ｜ 2,3,4`。

**落点**：规则下沉到 `lilist-model.sortLilist`（+ `hint-block-container.ts` 的内部列表同一规则），
所以**不只**「修改编号值」这一个入口生效 —— 任何触发重排的操作都会纠正；
而且 `core/index.tsx` 挂载时已有 `Editor.normalize(editor, { force: true })`
→ `withLilist` 批量 `sortLilist` → **旧文档一加载就自愈**（这是用户说「还是重复」的关键：
他看的是加载后没动过的旧数据，上一版只在点「确定」时才生效）。

**探针实测（真实源码）**：A `1,2,[2锚点],3,4` 重排 → `[1,2,3,4,5]`（锚点全清）；
B 两个 list_id → `[1,2,2,3,4]`（各自独立）；C 锚点设 5 → `[1,2,5,6,7]`；
D 在坏项上再输 2 → `[1,2,3,4,5]`；E 开始新列表+改值 2 → `[1,2,2,3,4]`；F 重排幂等 ✅。
`tsc -b` 0 报错。

**教训**：用户说「默认会转成3」时，我理解成「这一项变成 3」，并进一步做成「拒绝/夹住」；
实际是「**让列表去迁就用户的输入**（后面的项顺延），保证同一列表内不乱」。
下次遇到这类「默认会变成 X」的描述，先确认「是拒绝这个输入，还是重排其他项」。

## ⚠️⚠️ 真正的病根：markdown 输入 "2." 会强制另起列表（第三次才对）

用户截图里那个「2. 俄」是**在正文里输入 `2.` + 空格**造出来的（markdown 快捷键），
不是编号弹框。`withMarkdownShortcuts` → `convertBlockToLilist(editor, path, OL, startNumber)`，
而它原来的写法是：

```ts
const connectId = startNumber === 1 ? (查相邻列表) : undefined;   // ← startNumber≠1 永不承接
setLilist(..., list_id: connectId ?? uuidv4(), list_custom: connectId === undefined);
```

**起始号 > 1 → 一定新 uuid → 屏幕上出现「列表里已经有 2，又出现一个 2」**（数据上是两个列表，
用户看到的是一条连续列表）。这才是「还是重复」「改了半天一点作用都没有」的真实原因：
前两轮我只改了「修改编号值」和 sortLilist，**输入 `2.` 这条路根本没走到**。

**修复**（`lilist-commands.convertBlockToLilist`，含提示块内部行那条同构分支）：

- 起始号无论是不是 1，**先尝试承接相邻列表**（`getPrevConnectListId` / `getPrevHeadingConnectListId`）。
- `list_custom: true` 恒定，**是否跳号交给 `sortLilist` 裁决**：
  起始号 > 前方计数 → 跳号保留（输入 `5.` → 5,6,7）；否则顺延（已有 2 时输入 `2.` → 本项 3、后面 4,5）。
- 刻意要「另起一个从 2 开始的列表」→ 用编号弹框的「开始新列表」（这条路径不受影响）。

**探针实测（真实源码）**：① `1,2,[空段],3,4` 在空段输入 `2.` → `[1,2,3,4,5]` 且**同一 list_id** ✅（用户用例）；
② 输入 `5.` → `[1,2,5,6,7]`；③ 前面无列表输入 `3.` → `[3]`；④ 输入 `1.` 承接 → `[1,2,3,4]`。
`tsc -b` 0 报错。

**关键取舍（别再踩）**：**不能**做「相邻且编号重叠的两个列表自动合并」的自愈——
「开始新列表 + 改编号值」得到的手动拆分（`1,2 ｜ 2,3,4`）与 bug 产物的**数据结构完全一样**，
自动合并会把用户明确想要的拆分也吃掉。所以**旧文档里的坏数据只能靠「继续之前的编号」一次性合并修好**，
不能靠重排自动修（重排只能修「同一列表内」的越界锚点）。

**排查方法论教训**：连续两轮「改完没效果」，根因是**只覆盖了自己想到的那一个入口**。
列表编号有 5+ 个写入点（markdown 转换 / 回车 / 拖拽 / 块选择器 / 编号弹框 / 粘贴），
改这类规则前先用 `grep -rn "list_custom\|list_number" src` 把所有写入点列出来，逐个确认。

## 任务列表（TODO_LIST）回车行为 — 新增

用户需求：① 任务列表里回车换行，**新项默认未勾选**；② 若当前任务项**没有内容**再回车，
应**转成普通段落**（退出任务列表），而不是一直往下无限追加空任务项。

**成因**：`TODO_LIST`（`type: 'todo-list'`，勾选状态在 `attrs.checked`）是**独立块类型、不是 lilist**，
回车此前完全没被接管 → 走 `editor.insertBreak()` → `Transforms.splitNodes({always:true})`，
拆块时把 `attrs` 一并继承 → **新项连 `checked: true` 一起继承**（截图里那个空的已勾选项）。

**实现**（`src/events/keyboard/handleEnter.ts` 新增 `handleTodoListEnter`）：

- 空项（`Node.string(node).trim() === ''` 且 `path.length === 1`）→ `setNodes({ type: PARAGRAPH })`
  并 `delete attrs.checked`。
- 非空 → `splitNodes` 后取 `Path.next(path)`，**显式写 `checked: false`**。
- 分支位置：放在**提示块内部行分支之后**、lilist 分支之后——
  这样容器内部行仍走容器自己的 Enter 规则，不会被我截走。

**探针实测（真实源码）**：① 已勾选行尾回车 → `[todo(false), todo(true), todo(false)]` ✅（用户用例）；
② 空任务项回车 → `[todo, paragraph]` ✅；③ 中间回车 → 拆两项、后项 false ✅；④ 未勾选行尾回车 → 两项都 false ✅。

## ⚠️ 行尾陷阱：有些文件是 CRLF，别对它跑 prettier

`LilistSettingPopover.tsx` 是 **CRLF**（279 个 CRLF / 0 个 LF），而 `.prettierrc` 里

```
node -e "const b=require('fs').readFileSync(f);console.log((b+'').match(/\r\n/g)?.length||0)"
```

其它文件（FloatBar/index.tsx、locales 等）是 LF，可以放心 prettier。

## 块菜单图标列对齐（`ContextMenu.module.less` 的 `.actionIcon`）

用户指着块菜单左侧那一列图标说「没对齐」。

**成因**：`.actionIcon` 只有 `font-size`，**没有固定宽度** → 每行图标盒宽 = 字形自然宽度，
而菜单图标是混合字形（`☰` / `Aa` 是文字，`🎨💬✂📋🗑🌐` 是 emoji，`＋` 是全角），
于是图标中心与右侧标签起点每行都抖。

**实测（无头 Chrome + JS 量 `getBoundingClientRect`，见下）**：
修复前 **图标中心极差 4.7px、标签起点极差 9.4px**（Delete / Insert below 偏了 9px）；
修复后两者**都是 0.0px**。对比图存 `.workbuddy/artifacts/menu-icon-align.png`。

**修复**：`.actionIcon { flex: 0 0 20px; display: inline-flex; align-items:center; justify-content:center; line-height:1 }`
—— 20px 是**沿用项目既有约定**：`BlockTypePicker.module.less` 的 `.itemIcon` 就是 20px 居中，
`SettingsSwitcher` 的 `.rowIcon`(22px) 与 `FloatBar` 的 `.menuItemIcon`(22px) 也都是固定居中列。
**只有 ContextMenu 漏了**，所以这不是新发明，是补齐既有约定。

**已知的小差异（未动）**：块菜单行内边距 12px、块类型面板 `.item` 是 8px，

## 整块选中描边「贴身化」：不再圈住整行空白

用户反馈（4 张截图）：图片/流程图/附件卡片被整块选中时，蓝色描边画在**整行 wrapper** 上，
两侧圈出一大片空白，要求描边贴着插件内容、和插件完美贴合无空隙。

**根因**：`[data-whole-selected]` 的 outline 画在 `ElementWrapper`（块级 div，通栏 100% 宽）上，
而 void 插件的视觉内容（居中图片 / 固定宽流程图 / 420px 附件卡）比通栏窄。

**方案取舍**（重要，别再走回头路）：

- ❌ wrapper 选中时 `width: fit-content`：media 卡片（flex + max-width:420，无固有宽）会瞬间缩窄、
  chart（canvas 是 absolute，max-content≈0）会**塌缩成一条**、embed/日历等 width:100% 根也说不清——布局跳变风险太大。
- ✅ **实测覆盖层**：wrapper 保持通栏（零布局变化），选中时用 JS 测出「视觉根」相对 wrapper 的偏移，
  在 wrapper 内画一个绝对定位的贴身描边覆盖层。

**实现**：

- `ElementWrapper.tsx`：`FIT_OUTLINE_TYPES`（IMAGE/FILE/VIDEO/DRAWIO/COUNTDOWN/CALENDAR/CHART/EMBED/TIMELINE/DRAWBOARD，
  **DIVIDER 排除**——分割线本就通栏）。选中时 `measureFit()` 找 `wrapper.querySelector('[data-visual-root]')`
  （兜底 firstElementChild，行为=旧行为），getBoundingClientRect 求差值 → 渲染
  `.whole-block-fit-outline` 覆盖层（外扩 4px = 原 outline-offset 2 + 线宽 2）。
  ResizeObserver(wrapper) + resize + rAF 重测（media 换层会换掉视觉根节点，靠 wrapper 高度变化触发重测）。
  wrapper 加 `data-fit-outline='true'`。
- `index.css`：`[data-whole-selected][data-fit-outline]` 抑制通栏 outline；
  `.whole-block-fit-outline` 样式同原描边（border 2px + radius 8 = 6+2）。
- 9 个插件在**视觉根**上加 `data-visual-root`：image `.imageContainer`、
  media 三个 layer（card/text/view 同一时间只渲染一个）、drawio `.container`、chart `.card`、
  timeline `.frame`、embed `.frame`、calendar `.calendar`、countdown `.card`、drawboard `.card`。
  通栏类（embed/calendar 根 100%）标了也等于旧行为，无害。
- `data-whole-selected` 只被 CSS 消费（withDelete 行为层不依赖 DOM 属性），改描边不影响删除逻辑。

`tsc -b` EXIT=0。

### 追加：选中框合并成一层（用户：其实我更希望只有一层）

贴身化之后仍有两个框：插件自己的 selected 外框（box-shadow/border）+ 我们的贴身覆盖层。
合并方案：

- 覆盖层**外扩 4px → 0**：直接压在视觉根边框上（`border-radius` 6px 与根一致），视觉上就是一层框。
- 通栏容器（hint/table/code）的 `[data-whole-selected]` `outline-offset: 2px → 0`，同理压在自己边框上。

  image `.imageContainerSelected`、drawio `.containerSelected`、embed `.frameSelected`、
  drawboard `.cardSelected`、timeline `.containerSelected`（block 级）——less 规则 + TSX 条件类名都删。

  所以删掉插件 selected 样式不会出现「选中却没框」。

## 倒计时「结束气泡」不消失修复 + 可点击收起

用户反馈：到点的「⏰ 倒计时结束」气泡一直挂着不消失，也没法点掉。

**根因（dev 才会必现的 React StrictMode 坑）**：原实现 = effect 里 `notifiedRef` 防重入 +
setBubble(true) + 3s setTimeout；timer 的清理却放在**另一个 unmount effect** 里。
StrictMode 挂载→模拟卸载→再挂载时：模拟卸载把 timer 清了，再挂载又因
`notifiedRef.current === true` 直接跳过 → **timer 永远没机会触发 setBubble(false)** → 气泡常驻。
而且 `.bubble` 是 `pointer-events: none`，想点也点不到。

**修复**（`plugins/countdown/Countdown.tsx` + less）：

- 计时器清理收进**同一个 effect** 的 cleanup（deps `[remaining.finished]`，去掉 notifiedRef），
  重挂载后 effect 重跑、timer 重新武装；自动收起时长 3s → 5s。
- 气泡由 div 改 **button**：`pointer-events:auto` + cursor:pointer + hover 提亮，
  **点任意位置立即收起**，title「点击关闭提醒」。
- i18n：新增 `countdown.{finishedBubble, dismissBubble}` ×7 语言。

⚠️ 通用教训：**「定时自动收起」类一次性 UI，timer 的创建与清理必须放在同一个 effect 里**；
跨 effect 清理 + ref 防重入的组合在 StrictMode 下会让 timer 永久丢失。`tsc -b` EXIT=0。
